## 2. Key Assumptions

1. **Target platform** is AEM as a Cloud Service with **Edge Delivery Services** (document/content-source authoring), per Adobe's content-driven, three-phase performance model.
2. **Both EN + KO** are in scope for both sites (confirmed).
3. **Newsroom tag/taxonomy pages (~7,650)** are **not** migrated individually — they are produced by one tag-listing template + a query index. Only the **~3,250 articles** carry per-page migration effort.
4. Semiconductor **1,688** = target post-reduction structure. EN and KO share templates; content QA is counted per language where content differs.
5. **No net-new brand/design system** — design is extracted from the existing sites (Adobe design-token extraction), not designed from scratch.
6. Content migration is **automation-first**: reusable import pipelines (parsers + transformers) per template, followed by per-page QA — not manual re-authoring.
7. **Dynamic areas** (S.LSI Parts PD / PIM, CVE / product-security-updates) require integration work, not just content copy.
8. Samsung SMEs are available for IA sign-off, UAT, and content approvals within normal turnaround.
9. Estimate covers **build + migrate + launch + 2 weeks hypercare**. Post-launch BAU/ongoing authoring is excluded.

## 6. On-premise (AS-IS) vs. SaaS / EDS (TO-BE) — Architecture Comparison

| Dimension | AS-IS: AEM On-premise (+ WordPress) | TO-BE: AEM as a Cloud Service + Edge Delivery Services (SaaS) |
|-----------|-------------------------------------|--------------------------------------------------------------|
| **Hosting / Infra** | Self-managed servers (author/publish/dispatcher), OS patching, capacity planning | Adobe-managed cloud; auto-scaling; no server ops |
| **Two-site sprawl** | Two platforms (AEM + WordPress), duplicated ops | **Single consolidated platform** — one codebase, one ops model |
| **Performance** | Dispatcher + CDN tuning required; variable Core Web Vitals | Edge CDN by default; **100/100 Lighthouse achievable** via 3-phase loading |
| **Upgrades / patching** | Manual, project-based, risky | Continuous, Adobe-managed, near-zero downtime |
| **Authoring** | AEM component authoring; WP editor separately | Document/content-source authoring (Docs/DA), low training overhead |
| **Development model** | Java/OSGi bundles, build & deploy pipelines | Vanilla JS/CSS blocks, no build step, Git-based Code Sync — faster iteration |
| **Scalability (Newsroom 10K+ pages)** | DB/JCR load, publish queues | Edge-served static delivery; scales effortlessly |
| **Total cost of ownership** | High (infra + ops + upgrade projects) | Lower ongoing TCO (subscription; no infra/ops) |
| **Time-to-market** | Slower (release cycles) | Fast (push-to-publish) |
| **Multilingual (EN/KO)** | Supported, config-heavy | Supported via content-source folders + i18n |
| **Dynamic content (PIM/CVE)** | Custom Java services / integrations on-prem | Integrated via EDS blocks + APIs / query index (rebuild required) |

### Pros / Cons

**SaaS / EDS — Pros**
- No infrastructure or upgrade burden; Adobe-managed, always current.
- Best-in-class performance (edge delivery) — directly benefits SEO and the large Newsroom.
- Platform consolidation (retire WordPress + on-prem) → lower TCO and simpler ops.
- Faster development and publishing cadence; simpler authoring.
- Elastic scale for the 10K+ Newsroom footprint.

**SaaS / EDS — Cons / Considerations**
- Migration project effort required (this estimate) — dynamic areas (PIM, CVE) must be **re-integrated**, not lifted-and-shifted.
- Different authoring/dev paradigm → change management & training.
- Highly customized on-prem logic may need re-architecting to EDS blocks/APIs.
- Ongoing subscription cost vs. capitalized on-prem infra (commercial trade-off).
